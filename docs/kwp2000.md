# KWP2000 / ISO 14230-3 (`protocol/kwp2000.py`)

Keyword Protocol 2000 — the pre-UDS diagnostic protocol still used by a lot of
2000s-era ECUs, and the service layer under Ford's CAN GDS. The client mirrors
`UDSClient` almost exactly, so if you know one you know the other.

```python
from transport.socketcan import SocketCanTransport
from protocol.kwp2000 import KWP2000Client, Session

with SocketCanTransport("can0", ecu=0) as t:
    kwp = KWP2000Client(t)
    kwp.start_diagnostic_session(Session.EXTENDED)        # 0x10 0x92
    vin  = kwp.read_data_by_common_identifier(0xF190)     # 0x22
    dtcs = kwp.read_dtcs_by_status()                      # 0x18
    seed = kwp.security_access_request_seed(1)            # 0x27
    kwp.security_access_send_key(1, my_key(seed))
```

## How it differs from UDS

Same wire shape — request `SID [params]`, positive `(SID+0x40) [params]`, negative
`7F <SID> <NRC>`, and 0x78 response-pending is awaited transparently — but:

- **Local identifiers (LID, 1 byte)** exist alongside common identifiers (DID, 2
  bytes): `read_data_by_local_identifier(0x01)` vs `read_data_by_common_identifier(0xF190)`.
- **No suppress-positive-response bit.** `tester_present()` instead sends a
  response-required byte: `0x01` = respond, `0x02` = no response
  (`tester_present(response_required=False)` by default).
- **KWP addressing widths:** `read_memory_by_address` uses a 3-byte address + 1-byte
  size; download/upload use a 3-byte address + format + 3-byte size.
- **Sessions** are KWP ids: `Session.DEFAULT` (0x81), `ADJUSTMENT` (0x83),
  `PROGRAMMING`/`ECU_FLASH_REPROGRAMMING` (0x85), `ECU_DEVELOPMENT` (0x86),
  `EXTENDED` (0x92).

## Service coverage

| SID | Service | Method |
|---|---|---|
| 0x10 | StartDiagnosticSession | `start_diagnostic_session(session, data)` |
| 0x20 | StopDiagnosticSession | `stop_diagnostic_session()` |
| 0x11 | ECUReset | `ecu_reset(reset_type)` |
| 0x1A | ReadEcuIdentification | `read_ecu_identification(option)` |
| 0x14 | ClearDiagnosticInformation | `clear_diagnostic_information(group=0xFF00)` |
| 0x18 | ReadDTCsByStatus | `read_dtcs_by_status(status, group)` → `[{code,status,flags}]` |
| 0x17 | ReadStatusOfDTC | `read_status_of_dtc(dtc)` |
| 0x21 | ReadDataByLocalIdentifier | `read_data_by_local_identifier(lid)` |
| 0x22 | ReadDataByCommonIdentifier | `read_data_by_common_identifier(did)` |
| 0x23 | ReadMemoryByAddress | `read_memory_by_address(addr, size)` |
| 0x27 | SecurityAccess | `security_access_request_seed`, `security_access_send_key` |
| 0x2C | DynamicallyDefineLocalIdentifier | `dynamically_define_local_identifier(lid, def)` |
| 0x2E | WriteDataByCommonIdentifier | `write_data_by_common_identifier(did, data)` |
| 0x3B | WriteDataByLocalIdentifier | `write_data_by_local_identifier(lid, data)` |
| 0x30 | InputOutputControlByLocalIdentifier | `input_output_control_by_local_identifier(...)` |
| 0x31/0x32/0x33 | Start/Stop/Request Routine (by LID) | `start_routine_by_local_identifier`, … |
| 0x34/0x35/0x36/0x37 | Download / Upload / TransferData / TransferExit | `request_download`, … |
| 0x3E | TesterPresent | `tester_present(response_required=)` |

## DTCs (0x18 vs 0x17)

Both return `[{"code": "P0301", "status": 0x2F, "flags": {...}}]`, decoding the
2-byte DTC via `protocol.dtc.decode_dtc` and expanding the KWP `statusOfDTC` byte
with `decode_dtc_status`. Note the parsing difference the tests pin down: **0x18
carries a leading count byte**, **0x17 does not** (records follow the SID directly).

## Errors

`KwpNegativeResponseError(request_sid, nrc)` (with `.nrc_name` from
[`protocol/nrc.py`](negative-response-codes.md)), `UnexpectedResponseError`, and
`KwpTimeoutError` — the same shape as the UDS client's error set.

## Unlocking (0x27)

The `protocol.security` library works here too — `unlock()` accepts any client with
`security_access_request_seed` / `security_access_send_key`:

```python
from protocol.security import unlock
unlock(kwp, "SomeEcuName", 1)
```

See [security-access-0x27.md](security-access-0x27.md).
